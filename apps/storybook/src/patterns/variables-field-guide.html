01

The mental model

"Variable" is an umbrella over four genuinely different things. They share one storage shape and one reference syntax, but a builder meets them under different names, in different places, created by different actors.

↓
in — Input

Data the caller provides when the workflow starts. Grouped under whichever trigger node it belongs to; a connector trigger's inputs come pre-shaped from its manifest and can't be edited.

↑
out — Output

Data the workflow hands back on completion. Declared once at the workflow boundary; its value is whatever the author wires to it, or a literal default.

⛁
inout — Variable (state)

Internal, mutable, lives for the run. The only kind a node can write to mid-flow, via a per-node list of "variable updates" — an id plus an expression.

▢
node output — informal

Not declared by the author at all — it's whatever a node's own output definition says it produces. Becomes referenceable the moment the node exists; this is the largest category in most real workflows.

Storage shape — WorkflowVariable

Every declared variable (in / out / inout — not node outputs, which come from the node's own manifest) is the same Zod shape, defined once in flow-schema:

fieldpurpose
idUnique identifier, referenced in expressions as $vars.{id}.
direction'in' | 'out' | 'inout' — see legend above.
typeString tag — string / number / boolean / object / array / file.
subTypeOptional refinement (e.g. array item type).
schemaFull JSON Schema for object/array — authored via the visual Schema panel or a raw JSON toggle.
defaultValueOnly meaningful for in and inout.
descriptionFree text — doubles as intellisense hint text and (for agent outputs) as guidance to the model.
triggerNodeIdPresent only on root-level in variables — ties an input to the specific trigger node it belongs to.

Scoping is graph-shaped, not text-ordered

What's "available" at a node is computed fresh from the graph every time — getUpstreamNodes walks backward through edges (skipping loop-terminal edges so a loop body can't see its own future iteration), then getAvailableVariables collects every upstream node's outputs. Consequences a builder feels but rarely sees explained: a container (loop) node creates a nested scope — sibling loops at the same level can't see each other's variables, but a loop nested inside another loop still sees the parent loop's; a gateway's synthetic branch outputs are suppressed from every node except the one they were generated for; an error output only enters scope once a real edge is drawn from that node's error handle.

Two adjacent concepts that are not WorkflowVariable

Environment variables are project-scoped, not workflow-scoped — a flat key/value set for coded agents, backed by an EnvironmentVariablesService that the VS Code host swaps for a real on-disk .env file. File-type variables aren't a distinct direction, but every file variable gets a canonical shape silently backfilled ({ ID, FullName, MimeType, Metadata }) so its tree row renders consistently no matter where it was declared.

02

Where people actually touch them

Thirteen distinct surfaces, none of which is "the" variables feature — a builder assembles their understanding out of whichever ones they happen to hit.

Declare & manage
Variables panel docked panel, always mounted

The one place that lists everything at once — inputs by trigger, outputs, state variables, then one collapsible group per node that produces output. A "Selected node" toggle scopes the whole list down to what that node can actually see.

Add / edit variable dialog "+" on any section header

Name, type, description, a type-appropriate default-value field, and — for object/array — a visual schema builder or raw JSON toggle.

Rename dialog pencil icon next to a locked ID

Renaming is gated behind its own dialog because it has to rewrite every expression that references the old id — the dialog surfaces a live reference count before you commit.

Schema panel "Define schema" on an object/array variable

Simple/Advanced JSON Schema editor, shared with node input/output definitions — not variable-specific, but variables are one of its biggest consumers.

Reference in an expression
Variable picker type $ in any code field

Virtualized, keyboard-navigable tree grouped by prefix — $vars starts open, $self and $metadata start collapsed. Filtering force-expands whatever still matches. Data Fabric live references carry a LIVE QUERY badge with a tooltip summarizing the entity + query behind it.

Prompt editor Lexical-based, agent prompt fields

Variables render as pills inline in the prompt text rather than raw $vars.x strings — its own plugin model, not interchangeable with the CodeMirror/Monaco fields used elsewhere.

Code editor variable highlighting ambient, while typing

A CodeMirror decoration plugin colors $vars.x tokens distinctly from surrounding script — the only place a variable reference gets a visual identity outside the picker itself.

Assign a value
Variable update editor on a node, one row per assignment

The only place a node writes to state. Pick an existing inout variable or create one inline; the expression field defaults to a type-appropriate stub (0, [], true...) so it opens already in the right mode.

Output default-value field inside the add/edit dialog, direction = out

A workflow output's fallback value when nothing else maps to it — type-switches its own input control (text / number / switch / JSON textarea).

Configure a node's own I/O
Output variables editor agent / subflow node properties

Edits a node's own outputs definition — reuses the same add/edit dialog, with an extra "Required" switch for agent outputs (round-trips into outputSchema.required[]).

Subflow input / output editor on the subflow node, from the parent level

Renders in the parent's properties panel but writes into the child level it drills into — a deliberate break of the usual one-form-one-level rule.

HITL variable remapping human-in-the-loop task debug

Lets a reviewer re-point a task's inputs to different variables at debug time, without editing the node.

Adjacent surfaces
Input variables dialog just before starting a debug run

One field per entry-point input, including file upload — uploads happen out of band and the dialog only ever holds a reference to the result, never the file bytes.

Environment variables editor coded-agent project settings

Flat key/value list, deliberately outside the workflow-variable system described above.

04

How they're shown today

The panel is one component doing five jobs — filter, browse, disambiguate scope, create, and mutate — stacked in a fixed vertical order.

Panel anatomy, top to bottom

header
Either "Variables" or, when scoped, "Scope: {node label}" — plus the Selected node switch that toggles scoping on.
search
Free-text filter across id, name, type, and description — matches force sections and trigger sub-groups open and re-derive every count shown next to a header.
Inputs
Sub-grouped one level deeper, per trigger node — each trigger shows its own icon, label, and node id, with a nested tree for its input shape.
Outputs
Flat list of workflow-level out variables. Always rendered, even empty, so the "+" stays reachable.
Variables
Flat list of inout state variables. Same always-visible treatment.
per-node groups
One collapsible section per node that produces output — icon and label pulled live from the canvas, with a "focus" action that pans/zooms the canvas to that node and selects it.

Row anatomy

Every row shares one primitive (VariableItem / VariableTreeRow): a chevron if it has children, left-padding keyed to nesting depth, the value's type badge, and — only on hover — edit/delete actions so the resting state stays quiet. Object and array variables expand into a recursive schema tree in place, rather than opening a second surface.

Add/edit dialog

Name field validates against an identifier pattern live, with a same-tick check against every existing node id and variable id (collisions are illegal, not just discouraged). The instant the name is valid, a hint line appears showing exactly how it'll resolve in an expression — $vars.name for a plain global, $vars.{node}.output.{name} for anything tied to a trigger or an output node. Changing the data type resets the default value and — for anything other than object/array — silently drops any schema that had been drawn, so the dialog can never save a type/schema mismatch.

05

Live in this branch, right now

Worth knowing before sketching anything new: this exact area is mid-rework, uncommitted, on this branch.

uncommitted working-tree changes

The team's own next move is already sitting in the working tree — a real signal of where their thinking is headed, not a hypothetical:

  • The separate "Variables" tab is gone. It no longer sits beside Properties as its own tab or its own dockable panel — VariablesPanel now renders stacked directly beneath PropertiesPanel inside one scrolling column, divided by a plain border.
  • A new "Changes when this node runs" block appears above the variables list whenever exactly one node is selected — the VariableUpdateEditor is now generic and always available there, replacing the old approach of registering it per node-type as a form contributor (the update-variable contributor was just removed from the registry).
  • Search was just added to the panel itself — a plain text input filtering ids, names, types, and descriptions across every section at once, with per-section counts updating live to match.
06

Threads worth pulling

Observations, not recommendations — things that stood out while mapping the above that seem worth interrogating during concepting.

01
One list, four mental models.

Declared inputs, declared outputs, internal state, and node-produced values all live in the same flat panel today, distinguished only by section and a small color-coded icon. As workflows lean more agentic — more nodes producing more of their own outputs — that fourth, undeclared category keeps growing while the other three stay roughly fixed in size.

02
The reference syntax is the interface.

$vars.x shows up as the literal hint text in the add dialog, the placeholder text in the update editor, and the label in the picker. It's precise, but it's also implementation vocabulary surfacing everywhere a less technical builder looks for help.

03
No trace of "who wrote this last."

A state variable can be updated by any number of nodes scattered across the graph. Nothing in the panel today answers "which nodes write to this one" — you'd have to open every node's properties and check its update list individually.

04
Three editors, one underlying shape.

Workflow inputs, trigger inputs, and subflow inputs are all the same WorkflowVariable with direction: 'in', but a builder meets them through three differently-shaped editors depending on which boundary they're standing at.

05
Scale has no story yet.

The picker is virtualized because expression-time lookups can get long; the panel itself is not — every section renders in full. Search just landed as a first answer, but a workflow with a few hundred variables would still be a very long scroll.
