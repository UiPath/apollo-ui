## How translations are set up

Vertex components ship their own translations for every supported locale. They live in the `apollo-vertex` i18next namespace, so they never mix with your app's keys, and you don't copy them into your `en.json`.

Your app's own strings need their own i18next setup. Write a `configureI18n` function that initializes i18next with your catalogs and then calls `addVertexTranslations`, and pass it to `ApolloShell` or `LocaleProvider` (see [App translations](/patterns/shell#app-translations)):

```ts
// src/lib/i18n.ts
import i18n from "i18next";
import { initReactI18next } from "react-i18next";
import { addVertexTranslations } from "@uipath/apollo-vertex";

export const configureI18n = async () => {
  await i18n.use(initReactI18next).init({
    /* your config */
    fallbackLng: "en", // required
    interpolation: { escapeValue: false }, // required
  });
  await addVertexTranslations(i18n);
};
```

```tsx
<ApolloShell configureI18n={configureI18n} /* ... */ />
```

Two settings in this example are required:

- **`fallbackLng: "en"`:** a string without a translation shows in English, not as a raw key. Every new string is untranslated until the next weekly delivery, so without this setting users see keys such as `invoice_list_title`.
- **`interpolation: { escapeValue: false }`:** React already escapes values. Without this setting, a value such as `Q3 & Q4` shows as `Q3 &amp; Q4`.

Without `configureI18n`, the shell loads only the Vertex catalog and your keys don't resolve.

`addVertexTranslations` loads the current language and English, and loads other languages when the app switches to them. When a language already has `apollo-vertex` strings, such as your own overrides or those another copy of the package added, it adds only the missing keys and keeps the rest.

In a module-federated app, each remote bundles its own copy of the package. Call `addVertexTranslations` once from each remote as well, when the remote loads, with the shared i18next instance, so a remote built on a newer version adds the strings the shell's copy doesn't have. Each call adds a listener, which the function it returns removes.

The steps below cover your app's own strings. Each step roughly maps to a commit: follow them in order.

## 1. Update to the latest `@uipath/apollo-vertex`

The [Shell pattern](/patterns/shell) brings in the `LocaleProvider` and updated shell components that support i18n out of the box. Language switching is integrated into the user profile dropdown.

## 2. Add locale files under `src/locales/`

Create `en.json` (source of truth with all key-value pairs) and empty `{}` placeholder files for each supported locale: `de.json`, `es.json`, `es-MX.json`, `fr.json`, `ja.json`, `ko.json`, `pt.json`, `pt-BR.json`, `ru.json`, `tr.json`, `zh-CN.json`, `zh-TW.json`, `ro.json`

Use i18next with JSON locale files: Vertex uses it, and the localization pipeline is set up for it. If your repo already uses another i18n library, ask in **#product-localization** before you start.

## 3. Add the `jsx-no-literals` lint rule to prevent hardcoded strings from creeping back in

[https://github.com/jsx-eslint/eslint-plugin-react/blob/master/docs/rules/jsx-no-literals.md](https://github.com/jsx-eslint/eslint-plugin-react/blob/master/docs/rules/jsx-no-literals.md)

This ensures every user-facing string goes through the `t()` function.

## 4. Add translation keys and their English values to `en.json`

Replace all hardcoded strings in your components with `t("key")` using `useTranslation()` from `react-i18next`. Use `snake_case` for keys and `{"{{variable}}"}` for interpolation.

Follow the rules below for every key. They keep strings translatable and stop the TMS from receiving text it cannot parse.

### Counts

Use the first option that fits:

1. **A unit of measure** (time, size, percent): format the number and unit with `Intl.NumberFormat` in `i18n.language`, and pass the result as a placeholder: `"time_range_last": "Last {{duration}}"`. If the formatted value is the whole text, render it without a key.
2. **A count next to a heading, tab or chip label:** `"changes_tab": "Changes ({{total}})"`.
3. **A count in other text:** a count-neutral label, noun first: `"selected_items": "Selected items: {{total}}"`. Prefer this to `(s)` endings such as `"{{total}} file(s)"`: it reads naturally in every language, without leaving translators to improvise.
4. **A count that must read as a sentence, when 2 and 3 don't fit:** plural keys, with `_one` and `_other` only and a variable named `count`:

   ```json
   "files_selected_one": "{{count}} file selected",
   "files_selected_other": "{{count}} files selected"
   ```

   Call `t("files_selected", { count })`. Don't add `_zero`, `_few` or `_many` keys: the TMS doesn't support them. From `@uipath/apollo-vertex` X.Y, languages with more plural forms, such as Romanian and Russian, read the other forms from `_other` instead of showing English.

Never write:

- ICU plurals or selects, such as `{count, plural, one {# file} other {# files}}`. The TMS cannot parse them.
- Plural logic in code, such as `count === 1 ? "file" : "files"`. It is wrong in languages with more plural forms.

### States and variants

A different state is a different string. Use one key per state, chosen in code: `"filters_none": "No filters set"` and `"filters_count": "Filters set: {{total}}"`.

### No concatenation

Never build text from several keys, or from a key plus a variable word: word order differs between languages. Use one key with placeholders: `"assigned_to": "Assigned to {{name}}"`.

### One key per UI context

Don't reuse a key because the English matches. "Open" on a button and "Open" as a status may need different translations.

Name the key after its role and place (`invoice_list_delete_button`, not `delete`). Translators see the key name, so it is their main context.

### Changing a string

To reword the English, edit the value and keep the key: the change is picked up for translation, and existing translations stay in place until it is updated. When the meaning changes, create a new key instead. Otherwise users keep seeing the old translation, with the old meaning, until the new one arrives.

### Placeholders

Use double braces: `{{name}}`. Single braces are shown as plain text.

### Dates, numbers and units

Format dates, numbers, units and percentages with `Intl` in `i18n.language`, not the browser's language. Spacing around `%` and units differs between languages.

### No logic on translated text

Never filter, sort or compare using a translated label. Translations change, and the logic breaks with them.

### Context for translators

Translators see your text without the screen around it. Give them context in two ways:

- **Key names:** name each key after its role and place (see [One key per UI context](#one-key-per-ui-context)). This is their main context.
- **Visual context (optional):** the TMS can capture screenshots of strings in your running app. Ask the localization team in **#product-localization** if you want to set it up.

Translators' questions come back through dedicated Slack channels. Please support with a fast resolution if your help is requested in disambiguating strings.

### Room for longer text

Translations can be up to 40% longer than English, for example in German and Russian. Avoid fixed widths and truncated labels.

## 5. Add a CI check for unused translation keys

This catches stale keys in `en.json` that are no longer referenced in source code. Add a script and a CI job that fails if any orphaned keys are found.

## 6. Add localization coding standards to `AGENTS.md` (if the file exists in your repo)

Add this section so AI agents and contributors follow the same rules:

```md
## Localization

- Every user-facing string goes through `t("key")` from `react-i18next`. No hardcoded text in components, including labels, placeholders, tooltips and aria labels.
- Add keys to `src/locales/en.json` only. Never edit or create other locale files: the localization pipeline owns them.
- Keys are `snake_case` and name the role and place (`invoice_list_delete_button`). One key per UI context: never reuse a key because the English matches.
- To reword English, edit the value and keep the key. When the meaning changes, use a new key.
- Placeholders use double braces: `{{name}}`. No concatenation: never join keys or add words to translated text in code.
- Counts: use a count-neutral label (`"Selected items: {{total}}"`) or the count in parentheses (`"Changes ({{total}})"`). If a sentence needs a plural, use `_one` and `_other` keys with `{{count}}`, never other plural forms. Never ICU (`{count, plural, ...}`) and never `count === 1 ? ... : ...` in code.
- Format dates, numbers, units and percentages with `Intl` in `i18n.language`.
- Never filter, sort or compare using translated text.
- Check new UI with `?pseudo=1` before opening a PR, and with `?pseudo=keys` to see which key each string uses.
```

## Test before you merge

Developers own internationalization testing (see the [Internationalization Testing Guide](https://uipath.atlassian.net/wiki/spaces/EOPS/pages/89246204188)). One check covers most of it, and works before any translations exist: pseudo-localization. Add this plugin once, then open any page with `?pseudo=1`. Every translated string shows accented, 40% longer and in brackets. Formatting tags such as `<strong>` are left as they are. With `?pseudo=keys`, each string shows its key instead.

```ts
// src/lib/pseudo.ts
const ACCENTS: Record<string, string> = {
  a: "à", c: "ç", e: "é", g: "ĝ", i: "î", l: "ļ", n: "ñ", o: "ö", r: "ŕ", s: "š", t: "ţ", u: "ü", y: "ý",
  A: "Å", C: "Ç", E: "É", G: "Ĝ", I: "Î", L: "Ļ", N: "Ñ", O: "Ö", R: "Ŕ", S: "Š", T: "Ţ", U: "Ü", Y: "Ý",
};
const VOWEL = /[àéîöüýÅÉÎÖÜÝ]/;
const TAG = /(<[^>]*>)/; // formatting tags such as <strong> or <1>, left as they are

// 40% longer, by repeating vowels inside words: text grows like German words instead of wrapping at a space.
const lengthen = (text: string) => {
  const target = Math.ceil(text.length * 1.4);
  while (text.length < target) {
    const before = text.length;
    for (let i = text.length - 1; i >= 0 && text.length < target; i--) {
      if (VOWEL.test(text[i])) text = text.slice(0, i) + text[i] + text.slice(i);
    }
    if (text.length === before) text = text.padEnd(target, "~"); // no vowels, e.g. "CSV"
  }
  return text;
};

export const pseudo = {
  type: "postProcessor" as const,
  name: "pseudo",
  process: (value: string, key: string | string[]) => {
    const mode = new URLSearchParams(window.location.search).get("pseudo");
    if (mode === null) return value;
    if (mode === "keys") return Array.isArray(key) ? key[0] : key;
    const parts = value.split(TAG); // odd positions are tags
    const text = parts
      .map((part, i) => (i % 2 ? part : lengthen(part.replace(/[A-Za-z]/g, (c) => ACCENTS[c] ?? c))))
      .join("");
    return `[${text}]`;
  },
};
```

```ts
// in configureI18n
if (import.meta.env.DEV) {
  const { pseudo } = await import("./pseudo");
  i18n.use(pseudo);
}
await i18n.use(initReactI18next).init({
  /* your config */
  postProcess: import.meta.env.DEV ? ["pseudo"] : [],
});
```

`import.meta.env.DEV` is Vite's development flag, so production builds leave the plugin out. With another bundler, use its equivalent, or the plugin ships with your app (it stays off unless the URL has `?pseudo`).

On the screens you changed, look for:

- **plain English text:** it is hardcoded and does not go through `t()`
- **a missing closing bracket, or overlapping text:** the layout cuts off longer translations
- **brackets that end mid-sentence** (`[Hééļļöö], Sam!`): a sentence glued together from fragments
- **accents cut off at the top or bottom:** a fixed line height that is too tight for accented or Asian characters

If your feature has text input, search or dates, also check it once in Japanese after translations arrive: type 2 Japanese characters, search for them, and check the date format.

## Once your PR gets merged

1. Request onboarding to the localization pipeline in **#product-localization**. Include:
   - the repository name
   - the main development branch (for example `main` or `develop`)
   - the path to your source file (for example `src/locales/en.json`)
2. Give **andrei-stoian** (Localization team) read/write access to your repo. Translation PRs come from this account.

## After onboarding

- **Adding strings:** add new keys to `en.json` (by hand, or with an extraction tool if your repo uses one), in the same PR as the code that uses them. The localization pipeline picks up the new English once the PR is merged to the main development branch mapped during onboarding.
- **Translations arrive weekly.** At the end of each week, a PR delivers the translations for the strings merged the week before. Faster delivery is possible on request in **#product-localization**, but it isn't the standard process.
- **Translation PRs** come from **andrei-stoian**, on a branch named `localization_sync/...`, usually titled `chore(l10n): sync from Localization`. They change only the non-English files. Merge them as they are.
- **Never edit non-English files.** The next sync overwrites them. To report an issue with translations, post in **#product-localization**.
- **Until translations arrive,** users see English for new keys, as long as your setup has `fallbackLng: "en"` (see [How translations are set up](#how-translations-are-set-up)). Without it, they see raw key names.
