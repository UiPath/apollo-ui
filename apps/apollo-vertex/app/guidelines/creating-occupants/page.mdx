# Creating occupants

An occupant is the content inside a surface: a pattern that knows the space
it needs, and works in any surface that gives it that space. This page covers
how to design one. The [design architecture](/guidelines/design-architecture)
page covers the specs in detail.

## An occupant is a role

Occupant isn't a kind of component, and there's no separate section for
them. It's a role a pattern takes on when it has an occupant spec. The
[activity timeline](/patterns/activity-timeline) is a pattern first. Its spec
is what lets it go in a side panel or a content area.

- Occupant patterns live under Patterns, with an "Occupant" label and a
  "Where it fits" table made from the spec.
- Each surface page lists the occupants that fit it, also made from the
  specs.
- Occupants never name a template. A spec describes what the occupant needs
  from a surface, so it works in every template that has that surface.

## The spec

| Field | What it says |
| --- | --- |
| `name` | Rendered as `data-occupant`. Lowercase and hyphenated |
| `label` | Shown in docs and tooling |
| `icon` | A lucide icon, for pickers |
| `orientations` | The surface shapes it works in. Defaults to `["vertical"]` |
| `surfaces` | Only when it's built from one surface's own parts. Leave it out otherwise |
| `requires.minWidth` | The narrowest inner width where it still works |
| `requires.padding` | `padded` or `flush` |
| `requires.scroll` | `surface`, `occupant`, or `either` |

## View models and adapters

An occupant renders a neutral view model: the shape of its content, with no
domain in it. The activity timeline shows events with an actor, status,
title, detail, and time. It doesn't know about invoices, claims, or loans.

- Your solution maps its own data into the view model with an adapter.
- Adapters belong to the solution, not the occupant. The registry item never
  ships one.
- In this repo, example adapters live in an `examples/` folder next to the
  view model, and nothing outside `examples/` may import them. The dependency
  rules check this.
- Every occupant has at least two examples from different domains, and a
  stress example. The docs and checks render it with each.

## Minimum width is a design decision

`minWidth` is the narrowest inner width where the occupant still works. Set
it by measuring, not guessing:

1. Find the measured floor: the narrowest width where nothing clips, across
   every example, stress included.
2. Decide the minimum. It's at least the floor, and above it when the
   occupant gets hard to read before it breaks.

```bash
pnpm measure:occupant key-facts
```

It reports the floor for each example in each surface the occupant claims,
compares it with the declared minWidth, and fails if the declared width is
below the floor.

The stage strip declares {stageStripOccupant.requires.minWidth}px and the
activity timeline {activityTimelineOccupant.requires.minWidth}px. Both could
go narrower without clipping, but below those widths the current stage and
event titles get hard to read.

An occupant can also follow its surface: its minWidth reads the narrowest
surface's width token instead of a number, so it fits every such surface and
moves with the token. The queue follows the side panel: it declares
{queueOccupant.requires.minWidth}px, the side panel's minimum of
{LAYOUT_TOKENS.sidePanelWidthMin}px, because it runs edge to edge. The
measurement still checks that nothing clips there.

For the minimum to hold for any data, long values truncate or wrap:

- Truncate single-line labels, and keep the full text in a `title`.
- Wrap everything else, including long unbroken strings (`wrap-anywhere`).
- Handle missing and empty optional values.

## Orientations

Surfaces give a space with an orientation. The page header is horizontal: a
wide, short band. Side panels and the content area are vertical: columns that
grow downward.

- An occupant lists the orientations it works in.
- It adapts to the shape of the space with `useSurface()`, never to the
  surface's name. For style-only changes, use container queries.
- If it shows the same information in both shapes, it's one occupant with
  both orientations.
- If a smaller version shows different information, it's a separate
  occupant that shares the view model. The
  [stage strip](/patterns/stage-strip) is the timeline's summary: same data,
  different information, so a different occupant.

## Standard states

Every occupant renders the same states with `OccupantStateView`:

| State | What it shows |
| --- | --- |
| `ready` | The content |
| `loading` | Placeholders shaped like the content |
| `empty` | A short message about what will appear here |
| `error` | What failed, and Retry when the occupant is given `onRetry` |
| `agent-updating` | The content, still readable, marked busy, with a status line |

The state view adapts to orientation too: messages stack in a vertical
surface and sit in one row in a horizontal one.

## Recommended actions

When an occupant shows actions, at most one is recommended:

- The recommended action gets primary emphasis and stays visible.
- Its reason is available as a tooltip and as a description for assistive
  tech.
- Without a recommendation, every action gets equal emphasis, and any can
  fold into an overflow menu when space runs short.

The recommendation comes from the view model, so the solution decides it.

## Create one with the generator

Start from what the occupant shows. Describe its view model in a small JSON
file: the item type, the list's name, and each field with a kind.

```json
{
  "item": "KeyFact",
  "collection": "facts",
  "subject": "What the facts are about, for accessible names.",
  "fields": [
    { "name": "label", "kind": "label", "description": "What the fact is." },
    { "name": "value", "kind": "value", "optional": true, "description": "Its value, formatted." }
  ]
}
```

| Kind | How it renders |
| --- | --- |
| `title` | The item's main text. It wraps, or on a card, truncates with the full title in a tooltip |
| `label` | A short single line. It truncates, with the full text in a title |
| `value` | The value in a label and value pair. It shows "Not set" when empty |
| `detail` | Secondary text. It wraps |
| `meta` | Small text, like a time. It wraps |
| `figure` | A prominent value, like an amount. It sits at the end of the title's line |
| `status` | A label with a tone, shown as a colored dot, and a count of any more |

### Lists people work through

Three options in the view model file cover lists people work through, like a
queue:

| Option | What it adds |
| --- | --- |
| `"selectable": true` | Items render as cards people pick. The page owns the current item, through `currentId` and `onSelect`, and a footer steps through the items |
| `"groups": true` | Each item has a `group`, and items show under their group's label, with a count |
| `"filters": true` | The view model has `filters`, each item a `filter`, and tabs filter the list, with All first |

A selectable or filtered occupant keeps its tabs and footer in place and
scrolls its own list, so its scroll is `occupant`. It's vertical only.

```bash
pnpm create:occupant key-facts --view-model key-facts.json \
  --label "Key facts" --description "The few facts that matter most about an item." \
  --icon Info --orientations both --min-width 160 --padding padded --scroll either \
  --surfaces none --subject "key facts" --empty "Facts show here once there are some." \
  --primary-domain "shipment tracking" --secondary-domain "customer support"
```

`--min-width follow` makes the minimum follow the narrowest surface it
claims, instead of a guess to measure.

Anything left out, it asks for in plain terms. From those answers it writes, in
`registry/<name>/`:

- `<name>.occupant.ts`: the spec.
- `<name>.view-model.ts`: the view model, with each field's description.
- `<name>.tsx`: the component, rendering each field by its kind, wrapped in
  `<Occupant>` with the standard states, and reading `useSurface()` when it
  claims both orientations.
- `examples/`: a primary and a secondary adapter, one per domain, and a
  complete stress adapter made from the fields. Examples are always keyed by
  role, primary, secondary, and stress, so previews and checks can switch
  samples the same way for every occupant. None are shipped.

It also writes the Patterns page, and registers the occupant: a registry item
with the dependencies it imports, a path alias, the Patterns nav, its copy in
`locales/en.json`, and the occupant index. The checks, the docs, and any
preview with occupant pickers read the index.

What it can't know, like the two domains' sample data, it marks with one
placeholder token, and `pnpm check:placeholders` fails until every one is
filled in. It runs in lint.

Then measure, and set the minimum width:

```bash
pnpm measure:occupant key-facts   # report the floor
pnpm measure:occupant key-facts --apply   # set it to the floor
pnpm measure:occupant key-facts --set 160 --reason "Why it's wider than the floor."
```

In Claude Code, the `create-occupant` skill does this with you: it asks the
questions, runs the generator and the checks, and explains any failures.

A new docs page doesn't show until the dev server rebuilds its page list:
stop the dev server, run `rm -rf .next/dev`, and start it again.

## Checks

Every registered occupant is checked automatically, in every surface it
claims, with every example:

- No clipping from its minimum width up.
- Its spec fits exactly the surfaces its orientations claim.
- Light and dark themes.
- An accessibility scan with axe, in every standard state.

A set runs on every pull request, and a full sweep runs nightly.
