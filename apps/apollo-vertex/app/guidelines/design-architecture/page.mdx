# Design architecture

Pages in Apollo Vertex are built from three layers: templates, surfaces, and
occupants. Each layer has one job. Each has specs, written in TypeScript, that
say what it needs and what it provides.

## The three layers

| Layer | What it is | Examples | Where it comes from |
| --- | --- | --- | --- |
| Template | A page layout. It declares named slots and draws the lines between them. | [Detail page](/templates/detail-page), [List page](/templates/list-page) | Copied into your app |
| Surface | A container that fills one slot. It sets width, padding, scroll, and background. | [Page header](/surfaces/page-header), [Side panel](/surfaces/side-panel), [Content area](/surfaces/content-area) | The registry |
| Occupant | The content inside a surface. A pattern built from existing components. | A work queue, an activity history, the AI assistant, a data table | Your app or the registry |

## How they fit together

- Templates hold surfaces. Surfaces hold occupants.
- A template never holds an occupant directly.
- Each slot lists the surfaces it accepts.
- An occupant can be swapped for any other occupant that meets the surface's
  specs.

> Templates own the geometry between slots. Surfaces own everything inside
> their box.

So a template decides where things go and how wide each slot is. It draws
the dividers and owns the resize handle and the open and close motion. A
surface fills the slot it's given and decides its own padding, scrolling,
fades, and background. An occupant only decides its content.

## Specs

The specs live in `@/lib/composition`.

| Spec | Describes | Main fields |
| --- | --- | --- |
| `TemplateSpec` | A template | `name`, `slots` |
| `SlotSpec` | One slot in a template | `name`, `required`, `width` (`min`, optional `default` and `max`), `resizable`, `surfaces` |
| `SurfaceSpec` | A surface | `name`, `width` (its own minimum), `provides` (orientation, inner width, scroll) |
| `OccupantSpec` | An occupant | `name`, `label`, `icon` (optional), `surfaces` (optional), `orientations` (optional), `requires` (minimum width, scroll, padding) |

`fits(slot, surface, occupant)` checks that an occupant can go in a surface
in a given slot. It checks every requirement:

1. The slot accepts the surface.
2. The slot's inner width, with the occupant's padding, covers the occupant's
   minimum width.
3. The scroll owners agree.
4. The occupant works in the surface's orientation.
5. If the occupant lists the surfaces it works in, this surface is one of
   them.

It returns `{ fits, reasons }`. `reasons` lists every requirement that failed,
one plain sentence each. For an occupant too wide for the Detail page's start
panel, that reads "Needs Npx; the start-panel slot gives
{START_PANEL_WIDTH.default - 2 * PADDED_INSET_PX}px (padded)." `reasons` is
empty when the occupant fits. Padding has no check of
its own: every surface takes both paddings, and padding changes the inner
width, so it appears in the width reason.

A slot's inner width comes from its `width`: its `default` when it has one,
or its guaranteed `min` when it doesn't (a header that spans the page has no
default). A slot with no `width` falls back to the surface's own minimum.

Most occupants work in any surface of their orientations that gives them the
room. An occupant that belongs in only some of those surfaces lists them in
`surfaces`, and fits() rejects it anywhere else.

The helpers it uses are exported too: `slotAccepts`, `slotInnerWidth`,
`occupantPadding`, `occupantOrientations`, and `scrollCompatible`.

### Orientation

Every surface gives its occupant a space with an orientation:

| Orientation | The space | Surfaces |
| --- | --- | --- |
| `horizontal` | A wide, short band that doesn't grow downward | [Page header](/surfaces/page-header) (<Code>{pageHeaderSurface.provides.orientation}</Code>) |
| `vertical` | A column that grows downward and can scroll | [Side panel](/surfaces/side-panel) (<Code>{sidePanelSurface.provides.orientation}</Code>), [content area](/surfaces/content-area) (<Code>{contentAreaSurface.provides.orientation}</Code>) |

An occupant lists the orientations it works in as `orientations`. Most
occupants are columns of content, so it defaults to `["vertical"]`. fits()
rejects an occupant in a surface whose orientation it doesn't list.

> Occupants adapt to the shape of the space a surface provides, never to the
> surface's name. If a smaller version shows different information, it's a
> separate occupant that shares the same data mapping.

Inside a surface, an occupant reads the space with `useSurface()`, from
`@/lib/surface-context`:

```tsx
const { orientation, width } = useSurface();
```

- `orientation` is the surface's orientation.
- `width` is the live inner width in px, after the surface's padding. It is
  `null` until the surface has been measured.

For adjustments that only change styles, use container queries instead.
The side panel and content area make their inner area an inline-size
container, so an occupant can use Tailwind's `@sm:`, `@md:`, and so on. The
page header's container is its outer edge, which its own parts already
query.

### Minimum width

An occupant must render without clipping or overflowing at any width from
its minWidth up. minWidth is the narrowest width where it still works.

So set minWidth by testing the occupant at that width, not by guessing. If it
clips at its minWidth, the minWidth is too small.

## What surfaces own

Occupants never add outer padding. They declare what they need, and the
surface applies it.

| Setting | Values | What the surface does |
| --- | --- | --- |
| Padding | `padded`, `flush` | `padded` insets the occupant by {PADDED_INSET_PX}px on every side (`--surface-inset`). `flush` uses 0. |
| Scroll | `surface`, `occupant`, `either` | With `surface`, the surface scrolls and draws the fades. With `occupant`, the surface neither scrolls nor fades, and the occupant scrolls itself. `either` lets the surface decide. |

Each surface scrolls on its own. Scrolling main never scrolls a panel. The
page header never scrolls.

### Scroll fades

A scroll fade is a mask at an edge while there's more content in that
direction. It grows with the distance left to scroll, up to
{LAYOUT_TOKENS.scrollFadeSize}px, and doesn't animate. It's a mask, not an
overlay, so it works over any background.

- Surfaces that scroll draw their own vertical fades.
- An occupant that scrolls part of its content, like a wide table, uses
  `useScrollFade()` from `@uipath/use-scroll-fade` with the `axis` that part
  scrolls on, and the matching mask:

| Axis | Mask | Edges that fade |
| --- | --- | --- |
| `y` (default) | `SCROLL_FADE_MASK` | Top and bottom |
| `x` | `SCROLL_FADE_MASK_X` | Left and right |
| `both` | `SCROLL_FADE_MASK_BOTH` | All four. The two masks intersect (`mask-composite: intersect`), so an edge fades wherever either axis has more content. |

Left and right are physical edges. In right-to-left content, the fades follow
where the content remains.

Keyboard users have to be able to scroll too:

- A surface that scrolls takes keyboard focus while its content scrolls, and
  drops out of the tab order when it fits. Pass `focusable: true` to
  `useScrollFade()` for the same behaviour in an occupant, unless its content
  already has focusable elements.
- A mask hides anything painted outside the element, focus rings included.
  Draw a focusable scroll container's ring on an unmasked parent, as the side
  panel and content area do.

## Data attributes

Every layer renders a data attribute, so tools, tests, and styles can find it.

| Attribute | On | Value | Example |
| --- | --- | --- | --- |
| `data-template` | The template root | The template's name | `detail-page` |
| `data-slot` | Each slot | `<template>-<slot>` | `detail-page-main` |
| `data-surface` | The surface root | The surface's name | `side-panel` |
| `data-occupant` | The occupant root | The occupant's name | `queue` |

Surfaces also report their state: `data-padding`, `data-scroll`, `data-side`,
`data-state` (open or closed), and `data-placement`.

Naming rules:

- Lowercase and hyphenated.
- Named for what the thing is, not how it looks or where it sits. `side-panel`,
  not `left-drawer`.
- Sides are logical: `start` and `end`, not left and right. They flip in
  right-to-left languages.
- `data-slot` values include the template's name. shadcn components use
  `data-slot` for their parts, like `page-header-actions`, so the prefix keeps
  the two apart.

## Fixed and configurable

Most of a template is fixed: where slots go, the dividers, surface padding
values, backgrounds, motion, and the width rules. Teams configure only a few
things. On the Detail page that is which panels appear, where each panel sits,
and whether it starts open. Users can also resize the end panel.

Configurations are kept few on purpose:

- Every configuration is a combination to design, test, and support.
- Pages that share a template look and behave the same, so users learn one
  layout.
- A configuration is added only when a real need can't be met without it.

## Tokens

The layout values are theme tokens in `registry.json`. A script generates
`layout-tokens.ts` from them, so the CSS and the TypeScript specs read the same
numbers. `pnpm lint` fails if the two drift.

| Token | Value | Used for |
| --- | --- | --- |
| `--surface-inset` | {LAYOUT_TOKENS.surfaceInset}px | Surface padding |
| `--side-panel-width-min` | {LAYOUT_TOKENS.sidePanelWidthMin}px | The side panel's own minimum width |
| `--content-area-width-min` | {LAYOUT_TOKENS.contentAreaWidthMin}px | The content area's own minimum width |
| `--slot-divider-width` | {LAYOUT_TOKENS.slotDividerWidth}px | Divider line thickness. It takes no layout space. |
| `--scroll-fade-size` | {LAYOUT_TOKENS.scrollFadeSize}px | The longest a scroll fade gets |
| `--divider` | A lighter `--border` | Divider color. It matches the Shell sidebar's edge. |
| `--side-panel-tint` | `--sidebar` at {SIDE_PANEL_TINT_STRENGTH}% | Background of beside-header panels |
| `--panel-transition-duration` | {PANEL_TRANSITION_DURATION_MS}ms | Panel open and close |
| `--panel-transition-easing` | A `linear()` curve | Sampled from the Shell sidebar's spring |

## Known gaps

- **Small screens.** There is no overlay surface yet. On narrow windows the
  main-width rule closes panels instead.
- **Panel triggers.** There are no in-page controls to open or close panels
  yet. Your app opens and closes them through the template's state.
- **Start panel resizing.** The start panel has a width range in its spec but
  isn't resizable yet.
- **Registry.** Templates are copied into your app. They aren't registry items
  yet.
